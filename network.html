네트워크 코드 규격화와 캐시 처리

2022~ · 찍스 사진인화 등 · ㈜디지털포토

배경

서버에서 데이터의 갱신 버전을 관리하지 않아, 앱이 언제 새로 받아야 하는지 알 수 없었습니다. 그래서 갱신이 필요한 데이터는 새로 호출하고, 그 외에는 내부에 저장해 다시 쓰도록 앱에서 직접 나눠 관리했습니다. API가 많아도 같은 방식으로 다룰 수 있게 코드 모양을 규격화했습니다.

Retrofit 대신 직접 파싱한 이유

일부 API는 같은 값이 배열로 올 때도 있고 오브젝트로 올 때도 있었습니다. 예를 들어 페이지 안 사진이 여러 장이면 배열, 한 장이면 오브젝트로 내려왔습니다. Retrofit 은 응답을 Gson 으로 미리 정한 타입에 바로 넣기 때문에, 타입이 바뀌는 값은 그대로 쓰면 파싱에 실패합니다.

그래서 이런 API는 당시 통신 라이브러리(loopj android-async-http)로 응답 원문을 받아 org.json 으로 직접 파싱했습니다. 값의 종류를 먼저 확인하고, 오브젝트면 배열로 감싸서 항상 배열 하나로 처리하도록 통일했습니다. 응답 모양이 항상 같은 API(스티커·폰트 목록, 이미지 업로드 등)는 Retrofit 을 함께 썼습니다.

Object v = page.get("Image");
JSONArray images = (v instanceof JSONObject)
        ? new JSONArray().put(v)   // 한 장 → 배열로 감쌈
        : (JSONArray) v;           // 여러 장 → 그대로

2026.10 에는 업데이트가 끊긴 loopj 를 OkHttp 기반 호환 패키지로 교체했습니다. 호출 코드는 그대로 두고 import 만 바꿨기 때문에 이 파싱 방식도 그대로 유지됩니다. 이때 모든 인증서를 허용하던 코드도 지웠습니다.

Retrofit 으로 옮긴다면 같은 처리를 Gson 커스텀 TypeAdapter(JsonDeserializer) 한 곳에 두어, 앱 코드에서는 항상 리스트로 받게 할 수 있습니다.

규격 — API 1개 = 클래스 1개

호출 흐름 — 서버를 부를지, 저장된 값을 쓸지

호출 방법 비교

부르는 방법서버 호출쓰는 곳
get○○()없음화면 표시·가격 계산처럼 이미 받아 둔 값만 필요할 때 (바로 반환)
get○○(…, false, 콜백)저장된 값이 없을 때만있으면 쓰고, 없으면 받아야 하는 경우
get○○(…, true, 콜백)항상갱신이 꼭 필요한 시점

앱 시작 시 여러 API를 한 번에 준비

시작 화면에서 여러 API(업데이트 정보, 가격 정보, 액자 옵션 등)를 API마다 갱신 여부를 따로 받아 동시에 준비합니다. 필요한 것만 서버에서 받고 나머지는 저장된 값을 쓰며, 모두 끝날 때까지 기다린 뒤 메인 화면으로 넘어갑니다.

규격화해서 좋았던 점

  • 새 API를 추가할 때 같은 모양으로 클래스 하나만 만들면 됨
  • 화면 코드에서 메서드를 부르는 방법만 보고도 서버 호출인지, 저장된 값인지 구분됨
  • 서버 버전 관리가 없어도 갱신 시점을 앱에서 API별로 정할 수 있음
  • 응답 파싱 실패는 Crashlytics 에 기록하고 실패 콜백으로 전달하는 방식도 함께 통일
