2026.09~10 · 찍스·비비 8개 앱 · AI 코딩 도구 활용 · ㈜디지털포토

대응 방향

  • 폴더블 폰, 태블릿, 화면 회전, 화면 크기 조절(분할 화면 등)에 대응
  • 스마트폰에서 앱별로 고를 수 있는 표시 비율도 고려 — 앱 기본값, 전체 화면, 절반 화면, 기기 화면비, 16:9, 4:3, 3:2

문제 — 가로가 긴 기기에서 세로 영역이 커짐

기존 Play 스토어 버전은 S10 스마트폰의 가로 길이를 기준으로 비율 값을 정해 크기를 계산했습니다. 세로형 폰에서는 모두 비슷한 비율로 보였지만, 가로가 긴 기기에서는 세로 영역이 커지는 문제가 생겼습니다.

또한 대형 화면 기기의 전체 화면·멀티 윈도우 모드에서는 아래 설정이 무시됩니다.

설정역할
screenOrientation화면 방향(회전)
resizableActivity화면 크기 변경 허용
minAspectRatio / maxAspectRatio최소·최대 화면비
setRequestedOrientation() / getRequestedOrientation()화면 방향 고정

임시로 쓸 수 있는 PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY 는 targetSdk 37 로 올리면 무효화될 예정이라, 근본적으로 화면 크기 변화에 대응하는 방향을 택했습니다.

해결 1 — 기존 폰은 그대로, 넓은 화면만 예외 처리

기존 세로형 기기에서 보이는 크기는 바꾸지 않고, 가로형 기기만 예외적으로 처리했습니다.

순서계산의미
① 비율 크기짧은 변 × 디자인 값 / 375기존 방식 — 화면 폭에 비례 (S10 에서는 기존 배포와 같은 크기)
② 물리 크기디자인 값을 기준 기기 폭(dp)으로 환산 → 기기 density 로 px 변환어느 기기에서든 같은 실제 크기
③ 최종 값min(① , ②)폰은 ①과 같고, 넓은 화면에서는 ②가 상한이 되어 지나치게 커지지 않음

해결 2 — 화면비가 극단적인 기기는 아이콘 예외 처리

해결 3 — 회전·창 크기 변경 대응

  • 매니페스트: configChanges 에 orientation·screenSize·smallestScreenSize·screenLayout·keyboardHidden 추가
  • 회전·분할 화면 크기 조절은 화면을 다시 만들지 않고 onConfigurationChanged 에서 크기만 다시 계산
  • RecyclerView 스크롤 위치 유지, Fragment 탭 크기 재설정 확인
  • 폴드폰은 접었을 때·펼쳤을 때 기준값(아래 DesignDensity)이 바뀌므로, 이때만 화면을 다시 만들어 크기 재계산

제한 설정은 남겨 두고, 지울 때를 대비해 미리 구현 (셀프증명)

Q/A 담당자가 바빠 회전·창 크기 변경을 전부 다시 검수받기 어려운 상황이었습니다. 그래서 배포 버전의 화면 제한 설정은 지우지 않고 그대로 두고, 대응 코드는 미리 넣어 나중에 설정을 지워도 바로 대응되게 했습니다.

배포(release)디버그(debug)
화면 방향portrait 유지fullSensor (회전 허용)
제한 설정minAspectRatio="1.7", resizeableActivity="false", PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY — 그대로 둠
대응 코드configChanges, 회전 시 서버 재호출·편집 값 초기화 없음, 화면이 다시 만들어져도 주문 업로드 이어짐 — 양쪽 모두 포함

화면 방향은 빌드 설정(manifestPlaceholders)으로 나눠, 디버그 빌드에서만 회전·창 크기 변경을 확인했습니다.

해결 4 — DesignDensity: 크기 값을 XML 한 곳에서만 관리

기존에는 layout.xml 에 적은 크기를 Java(SizeUtilsNew)에서 화면 폭 비율로 다시 계산했습니다. 그래서 같은 값을 XML 과 Java 두 곳에 적어야 했고, 한쪽만 고치면 화면이 어긋났습니다.

순서내용
① density 재정의화면(Activity)의 attachBaseContext 에서 density 를 “디자인 1단위 = 해결 1의 최종 값”이 되도록 바꿈 → XML 에 적은 dp 가 곧 SizeUtilsNew 계산 결과
② 기준값이 바뀔 때폴드 접기·펴기처럼 적용할 density 가 달라지면 화면을 다시 만듦. 분할 화면 비율 조절은 최대 창 크기가 그대로라 다시 만들지 않음
③ 단계적 전환SizeUtilsNew 는 화면 px 기준이라 density 를 바꿔도 결과가 같음 → 기존 Java 계산 코드를 한 번에 지우지 않아도 됨

부작용과 대비 — 사람과 AI 모두 놓치지 않게

density 를 바꾸면, 화면 컨텍스트로 직접 만든 비트맵 이미지(setImageBitmap, new BitmapDrawable)의 크기가 비트맵 픽셀과 5~10% 달라집니다. 화면에서 티가 잘 안 나서 새 코드에서 실수하기 쉽다고 판단해 두 겹으로 막았습니다. (Glide 로 불러온 이미지는 앱 전체 Resources 를 써서 영향이 없음을 폴드4 에서 확인)

대비내용
빌드 검사design-density-guard.gradle — 빌드할 때 소스를 정규식으로 검사해, 위험한 코드(new BitmapDrawable, 이미지 매트릭스 직접 계산 등)가 있으면 빌드를 멈추고 고칠 방법을 메시지로 안내. 규칙을 문서로만 두지 않아서 AI 도 빌드 과정에서 스스로 감지하고 고칠 수 있음
디버그 화면 감시빌드 검사가 못 잡는 경우를 위해, 디버그 빌드에서는 화면을 그릴 때 이미지 매트릭스가 비트맵 픽셀 기준으로 계산된 ImageView 에 빨간 테두리를 그리고 로그를 남김
헬퍼 함수Drawable 크기 구하기, 비트맵 픽셀 크기 그대로 보이는 Drawable 만들기 등 바른 방법을 함수로 제공

검토한 대안

방식장점선택하지 않은 이유
화면 크기별 레이아웃 분리 (sw600dp, WindowSizeClass)안드로이드 권장 방식, 비트맵 부작용 없음8개 앱의 모든 화면을 다시 설계해야 해서 ‘기존 폰 화면 유지’ 목표와 맞지 않음
화면 폭별 dimens 파일density 를 바꾸지 않음모든 크기를 @dimen 으로 바꿔야 하고, 폴드처럼 중간 크기 기기는 정확하지 않음
Java 계산 유지위험 없음XML·Java 이중 관리 문제가 그대로 남음

새로 만드는 화면이나 태블릿 전용 화면은 화면 크기별 레이아웃 분리 방식이 맞다고 보고 있습니다.

결과

찍스·비비 8개 앱의 화면 크기 계산을 같은 방식으로 통일했습니다. 기존 폰에서 보이는 크기는 그대로 유지하면서 폴드 펼침·태블릿 같은 넓은 화면에서만 크기를 제한했습니다.
