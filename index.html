1. 난독화(R8) 도입 — AI 결과를 그대로 쓰지 않고 위험 요소를 직접 판단, 빌드 단계 안전장치 추가 (8개 앱)2026.09~10
배경
Play Console에서 ‘DEX 코드 최적화 기준 미달(난독화 1%)’ 경고 → 난독화 도입 필요
위험
조사해 보니 난독화 후 저장해 둔 사용자 데이터(장바구니, 설정 등)를 읽지 못해 실제 배포된 앱에서 오류가 날 위험이 큰 기능이었음
해결
  • AI에 맡기기 전에 위험성을 직접 조사하고 작업 범위를 정해 요청 — 저장 데이터 모델 패키지 정리·@Keep, 앱별 API에 맞는 규칙, 전체 파일 검사, 놓친 부분은 물어보고 진행
  • AI가 빌드를 통과시키려고 넣은 dontwarn(경고 숨김)을 제거 — 경고를 숨기면 클래스 누락이 실행 중 크래시로 나타날 수 있어, 경고는 원인을 확인한 뒤 필요한 것만 추가하는 기준을 정함
  • @Keep은 코드에만 있어서 이후 구현하는 사람이나 AI가 실수로 빠뜨릴 수 있다고 판단 → 빌드할 때 위험한 코드를 검사해 빌드를 멈추는 코드(r8-guard.gradle)를 AI에 요청해 추가 — 규칙을 문서로만 두지 않고 빌드 실패로 드러나게 해서, AI가 코드를 고친 뒤 빌드하면 스스로 감지하고 고칠 수 있도록 함
결과
8개 프로젝트에 적용, 배포 후 관련 오류 없음 (자세한 과정 보기)

배경
OpenCV가 일부 기기에서 로딩에 실패하고, Android 16KB 페이지와 호환되지 않고, 앱 용량을 키움. 단계적 축소를 반복하며 대비·채도가 조금씩 변하는 문제도 있었음

검증

결과
OpenCV 결과와 픽셀 차이 0~1 유지, 셀프증명 APK 49.9MB → 36.8MB (검증 과정 보기)
3. 셀프증명 코드 최신화 — 바뀐 코드를 익히는 개발자 학습 페이지 제작 (찍스 셀프증명, AI 활용)2026.10
배경
AI를 도입해 셀프증명 코드를 최신화(Java → Kotlin·코루틴 전환, Hilt 의존성 주입 적용)하면서 코드 구조가 크게 바뀜
해결
  • AI 작업은 한 번에 맡기지 않고 에러 수정 → lint → Kotlin 전환 → 코루틴·Hilt 순서로 나눠 진행. 단계마다는 바뀐 부분만 확인하고, Q/A 요청 전 전수 검사 (자세한 과정 보기)
  • 바뀐 코드를 개발자가 읽고 고칠 수 있도록 학습 페이지 2종을 AI에 요청해 제작 — Kotlin 유지보수 교육(10장, 마무리 퀴즈), Hilt 입문
  • 실제 셀프증명 코드(장바구니 주문 업로드 등)를 예제로, 무엇이 바뀌었는지 → 핵심 개념 → 자주 하는 작업 레시피 → 에러·함정 순서로 구성
4. 폴더블·태블릿·가로형 화면 대응 — 기존 폰 화면은 그대로 두고 넓은 화면만 예외 처리 (찍스·비비 8개 앱, AI 활용)2026.09~10
배경
기존 배포 앱은 S10 가로 길이 기준 비율로 크기를 계산 → 세로형 폰에서는 문제없었지만 가로가 긴 기기(폴드 펼침·태블릿)에서는 세로 영역이 커지는 문제. 대형 화면에서는 화면 방향·크기 제한 설정(screenOrientation, resizeableActivity, min/maxAspectRatio)도 무시됨
해결
  • 기존 세로형 폰은 그대로 두고 가로형·넓은 화면만 예외 처리 — 크기 계산을 ‘화면 비율 크기’와 ‘실제 물리 크기(dp)’ 중 작은 값으로 바꿔, 폰은 기존 배포와 같은 크기·넓은 화면은 상한 적용
  • 레이아웃 크기를 XML과 Java 두 곳에서 따로 관리하던 구조 정리 → 화면 density 자체를 디자인 기준으로 바꾸는 DesignDensity를 만들어, XML에 적은 dp가 곧 계산된 크기가 되게 함
  • density를 바꾸면 코드로 만든 비트맵 이미지 크기가 5~10% 달라지는 부작용 확인 → 빌드 검사(design-density-guard.gradle)와 디버그 빌드 화면 감시(어긋난 이미지에 빨간 테두리·로그)로 사람과 AI 모두 놓치지 않게 함
  • 화면비 2.4 이상·1.3 미만 기기(21:9 = 2.33, 4:3 = 1.33 기준 밖)는 특정 아이콘 수치 예외 처리
  • 회전·창 크기 변경 대응 — 회전·분할 화면 크기 조절은 화면을 다시 만들지 않고 크기만 다시 계산, 폴드 접기·펴기처럼 기준값이 바뀔 때만 화면을 다시 만들고 스크롤 위치·탭 크기 유지
  • Q/A 일정을 고려해 배포 버전의 화면 제한 설정(minAspectRatio 1.7, resizeableActivity=false 등)은 그대로 두고 대응 코드만 미리 구현 — 디버그 빌드에서만 회전을 허용해 확인, 나중에 설정을 지워도 바로 대응되게 함 (셀프증명)
결과
찍스·비비 8개 앱의 화면 크기 계산을 같은 방식으로 통일 (자세한 과정 보기)

해결

배경

배경
개발하면서 UX가 어색해 보이는 부분은 요청한 담당자와 이야기하며 정해 나감
의견
  • ‘화살표를 누르면 위로 올라가게’ 요청 → 헤더의 그림자 효과 때문에 헤더 전체가 버튼처럼 보여, 화살표가 아니라 헤더 전체를 누르는 영역으로 바꾸자고 제안
  • ‘하단 탭을 누르면 맨 위로 올라가게’ 요청 → 다른 탭으로 이동할 때는 기존 탭 위치를 유지해야 하므로, 이미 선택된 탭을 한 번 더 눌렀을 때만 맨 위로 올라가게 하자고 제안
8. 통신 라이브러리 교체 — 지원이 끝난 loopj를 OkHttp로, 인증서 검사 우회 제거 (8개 앱, AI 활용)2026.10
배경
통신에 쓰던 loopj(android-async-http)는 업데이트가 끊긴 라이브러리였고, 모든 인증서·호스트를 허용하는 코드(getFixedSocketFactory)가 있어 중간자 공격에 열려 있고 Play 보안 경고 대상이었음
해결
  • loopj와 같은 사용법의 OkHttp 기반 호환 패키지를 만들어 8개 앱에 같은 코드로 적용 — 호출 코드는 import만 바꾸고, 콜백 순서·스레드·실패 처리는 기존과 같게 맞춤
  • 인증서 검사 우회 코드를 지우고 OkHttp 기본 검사(안드로이드 신뢰 저장소) 사용 — 운영 서버 인증서가 정상인지 먼저 확인
결과
8개 앱에 적용, 그중 6개 앱 배포 완료 (2026.10)

2. 사진 선택 화면 확대·축소 애니메이션 커스텀 구현 (찍스 셀프증명 등)2024.10
배경
회사에서 기본 갤러리 앱처럼 핀치 줌 시 애니메이션 효과를 요청 — 성능 문제와 개발 기간이 늘어날 수 있다고 미리 공유했고, 괜찮다는 답변을 받아 진행
해결
2개의 가상 RecyclerView로 바뀌기 전 열 수와 바뀐 뒤 열 수의 배치를 미리 계산하고, 두 좌표 위치를 바탕으로 확대·축소 애니메이션 구현
결과
기존 3~5열 구성은 유지하면서, 열 수가 툭 끊기며 바뀌던 화면을 애니메이션과 함께 자연스럽게 바뀌도록 개선 (버벅임 없음) (원리 그림 보기)
3. 포토북 복잡한 뷰 터치 조작 기능 구현 (찍스 포토북)2020.03 ~ 2020.08
배경
2020 포토북 편집기 리뉴얼(전면 재작성) 과정에서 사진·사진틀·스티커 뷰의 줌, 이동, 뷰 터치 등 터치 관련 동작을 새로 구현
해결
  • ActionEvent를 활용해 사진·포토북·스티커 뷰별 공통 동작을 기준으로 먼저 구현한 뒤, 뷰마다 필요한 기능을 추가로 바꿔 제스처끼리 충돌하지 않도록 구성
  • 스티커를 화면보다 크게 늘릴 수 없던 문제 — 테스트 중 RelativeLayout에서는 뷰 가로 길이가 화면 너비를 넘지 못하는 등 RelativeLayout과 FrameLayout의 동작 차이(API 동작 차이)를 발견, 스티커 부모를 FrameLayout으로 바꾸고 부모 뷰의 잘라내기(clipChildren)를 해제해 해결 (2020.03 발견 → 2020.08 해결)
  • 확대 상태의 터치 처리 — 확대 배율만큼 터치 좌표를 보정하고, 두 손가락 줌이 시작되면 사진 뷰의 길게 누르기·클릭을 끄고 터치를 줌 레이아웃으로 넘겨 줌 인/아웃 중 사진 클릭이 안 되던 오류 수정
  • 겹친 뷰의 터치 충돌 — 편집 화면 뒤쪽 뷰가 눌리는 현상, 투명 화면 안 사진틀이 선택되는 현상, 스티커를 처음 누를 때 삭제·크기 조절 버튼이 같이 눌리는 문제 수정
  • 글자 크기를 많이 줄이면 실제 위치와 어긋나는 문제 — 칸 너비에 맞는 글자 크기를 이분 탐색으로 계산하도록 변경
결과
스티커 크기 조절·회전, 사진 위치 변경, 표지 영역 이동 범위 제한 등 편집 화면 터치 동작 구현 — 2020 포토북 편집기 리뉴얼에 포함

해결

  • ExifInterface도 성능이 느려 스레드 풀로 여러 사진을 동시에 읽는 병렬 처리 방식으로 변경 (2022.02)
  • 동시에 처리하는 개수를 무작정 늘리면 오히려 느려져, 개수를 적게·중간·많게 바꿔 가며 회사 테스트 기기(갤럭시 S22·S9, Android 5 기기 등)별로 모두 확인한 뒤 스레드 5개로 설정
결과
